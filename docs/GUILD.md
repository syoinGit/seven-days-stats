# 無人の冒険者ギルド（軽量初期版）

## 実装範囲

- 公開の `/guild`：酒場（ドットの部屋）が唯一の画面。日付固定の最大5人の来店、朝・昼・夜の様子。入口はどのサイトでもヘッダー右のジョッキと剣のアイコン。
- 画面下のタブ（酒場・来店者・住人名簿・掲示板・記録、管理者にはメンテ）から、各ページを酒場の上のウィンドウとして開く。
  - `/guild/visitors`：今日の来店者。`/guild/board`：いちばん新しい住人と記録棚。
  - `/guild/characters` と `/guild/characters/{id}`：永続する住人名簿・人物詳細（この街での関係・最近の交流つき）。原記録は非公開。
  - `/guild/log`：交流の記録（新しい順、30件ずつ）。住人・種類・今の関係で絞り込める。`/guild/log/{id}`：1件の場面と関係の変化。`/guild/pairs/{小さいID}-{大きいID}`：二人の物語。
  - どのURLも、酒場の上にそのウィンドウを開いた状態でサーバーが描く（JSなしでも、共有リンクでも同じ見た目）。JSがあれば、ギルド内のリンクはページ遷移せずにウィンドウを差し替え、URLも追従する（戻るで閉じる）。
- 管理者専用 `/guild/maintenance`：住人の追加・再試行（1日 `GUILD_DAILY_LIMIT` 人まで、既定10）、今日の来店者の引き直し、住人の削除、直近30件の実行結果。ポータルのメンテページから移動できる。
- 毎日21:00 **Asia/Tokyo** に、その日まだ誰も迎えていなければ1人追加する。
- 毎時3分 **Asia/Tokyo** に、今日の来店者のうち2人が交流する（下の「毎時の交流」）。
- 人物は名前・年齢・性別・職業・名前の系統・見た目・紹介・人となりを持つ。
- 人物は Bedrock の構造化出力を検証して保存。既存 `app.ai.model-id`、リージョン、AWS認証、`BedrockTextClient` を再利用する。画像APIは不要。

軽めの初回実装として、自動冒険、数値気質、世界情勢・情報伝達・英雄、死亡を確定させるイベントは未実装。記録棚にはこの段階を明記しており、存在しない冒険記録は表示しない。生存・負傷・行方不明・死亡を保存でき、存命以外は通常来店から除外、人物詳細は残す。生死を変更する管理操作やランダムな死亡処理は用意していない。

## 有効化

Flyway V52 は既存テーブルを変更せず、ギルド専用のテーブルを作成する。V53（Java）は1日1人の一意制約を外し、V54 は年齢・性別・職業と記憶の見出しを追加する。V55 は名前の系統・見た目のパーツと、記憶の種類を追加する。

```dotenv
GUILD_ENABLED=true
GUILD_RECENT_DAYS=30
GUILD_RECENT_RATIO=0.5
GUILD_DAILY_LIMIT=10
GUILD_FEMALE_RATIO=0.5
GUILD_CATEGORY_WINDOW=10
GUILD_CATEGORY_CAP=3
# 任意。公開する実際のURLが確定してから指定する。
# GUILD_PUBLIC_URL=https://<公開ホスト>/guild
```

既定では生成は無効。Bedrockを呼べる本番環境で `GUILD_ENABLED=true` を設定してアプリを再起動する。`app.ai.enabled` は既存の投稿スケジュールのスイッチであり、ギルドとは別。既存のAIモデル設定・AWS権限がそのまま必要。

有効時、起動30秒後から毎分、当日の来店名簿が未作成なら確定する。生成済み名簿は再抽選しない。新顔・久しく来ていない住人を優先し、ゲームの稼働状態は参照しない。人物がゼロなら空の日を確定せず、最初の誕生直後に来店できる。名簿確定後に追加した人物は新顔・名簿には即時表示され、来店は翌日以降。停止中の最終名簿を表示するときはその日付を明示する。

朝は00:00〜10:59、昼は11:00〜17:59、夜は18:00〜23:59（JST）。各時間帯の短い行動文をDBに保存し、閲覧では生成も書き込みも行わない。再読み込みで現在の時間帯を表示する。動きを減らすOS設定に対応。

## 記憶（出典）の選び方と公開範囲

住人は「記憶」から生まれる。記憶は、あるゲームの過去の1日（今日より前）の、日本時間で3時間の枠（0〜3時、3〜6時…）にある記録から最大10件を時刻順に並べたもので、ひとつの「種類」（釣り、ブラッドムーン、遠出…）を中心にする。

1. 直近30日とそれ以前を既定50:50で選ぶ（`GUILD_RECENT_DAYS` / `GUILD_RECENT_RATIO`）。候補がない側は反対側へ。
2. 使える記憶のあるゲームを均等に選ぶ。
3. そのゲームで実際に記録のある種類を均等に選ぶ。
4. その種類の記録を含む、まだ使っていない3時間枠を均等に選ぶ。同じ枠（ゲーム・日・枠）は2回使わない。
5. 10件のうち最大7件をその種類の記録から、残りを同じ枠のほかの記録（接続など）から選ぶ。

偏りの上限: 直近 `GUILD_CATEGORY_WINDOW`（既定10）人のうち、同じ種類の記憶から生まれるのは `GUILD_CATEGORY_CAP`（既定3）人まで。上限に達した種類しか残っていない日は、追加を見送る（SKIPPED）。

種類と、それを示す記録（記録が実際にある種類だけが候補になる。存在しない種類は作らない）:

| ゲーム | 種類: 記録 |
| --- | --- |
| 7 Days to Die | ブラッドムーン: ブラッドムーンの夜の枠（その枠の討伐もブラッドムーン扱い）。戦い: 討伐・ゾンビの群れ・スクリーマー・戦闘でのレベルアップ。倒れた夜: 死亡。探索: 建物の奥へ踏み込む（スリーパー）・補給物資・物資探しでのレベルアップ。採集: 採集でのレベルアップ。遠出: 乗り物で50m以上の移動 |
| Terraria | 釣り: 魚・木箱が増えた。採掘: 鉱石・インゴットが増えた。建築: ブロック・家具が増えた。狩り: 図鑑の討伐数の変化。大物との戦い: 進捗の達成（ネタバレ扱いの項目は除く） |
| Core Keeper | 探索: 洞窟へ降りた（接続）。料理: 食べ物が増えた。畑仕事: 種が増えた。採掘: 鉱石が増えた。建築: 設置物が増えた。大物との戦い: 進捗の達成（ネタバレ扱いの項目は除く） |

接続・切断やアイテムの減少は、どの種類にも数えず、記憶の文脈としてだけ使う。釣り・種の判定はアイテム名（サーバー上の名前表）による。名前表やアイテム分類がないと、Terraria / Core Keeper のアイテムはどの種類にもならない。

プレイヤー名・ID・座標・チャット・チェストの名前は読まない。記録の「誰か」は誰なのか分からないように書く。Terraria / Core Keeper の記録の時刻は、サイトが変化を確認した時刻。

記憶の見出し（例: 「Terraria・10月3日 21時〜24時の記録（釣り）」）と記録の行は、人物ページの「生まれた記憶」に公開する。ソースキー（ゲーム・日・枠）は非公開。AIに渡すのは見出し・種類・記録の行だけ。住人を削除すると、その記憶はまた使われることがある。

メンテページの「記憶の内訳」に、ゲーム・種類ごとの未使用の時間帯の数と、直近の住人の種類を表示する。

### ブラッドムーン偏重の調査（2026-10-25、コードの確認のみ）

本番DBは見ていない。コードから分かった原因は次のとおり。

- #91 より前の版は、AIに「ある一日の接続記録。接続回数=N。行動や戦果は不明。」としか渡していなかった。中身のない入力と「7 Days to Die」という名前から、AIがゲームの代表的な出来事（ブラッドムーン）で人物像を埋めていたと考えられる。#89 時点で生まれた住人の偏りは主にこれ。
- #91 の版は実際の記録を渡すようになったが、7DTDで読む記録が討伐・接続・死亡・ブラッドムーンだけで、戦闘の色が強かった。さらに、ゲームの次は日を均等に選ぶだけで、記録の多い夜（ブラッドムーンの夜は討伐が集中する）の枠がそのまま選ばれやすかった。
- 対応: 種類の段を追加して種類ごとに均等に選ぶ、7DTDで探索・採集・遠出の記録も読む、ブラッドムーンの夜をひとつの種類にまとめる、直近の住人の種類に上限を設ける。実データでの分布は、デプロイ後にメンテページの「記憶の内訳」で確認する。

## 性別・職業・見た目・名前

- 性別は女性・男性を `GUILD_FEMALE_RATIO`（既定0.5）でコードが抽選する。創作設定であり、元プレイヤーの属性は推測しない。
- 職業は記憶の種類から重み付きで抽選する（例: 釣り→漁師・料理人・農家、ブラッドムーン→夜警・騎士）。職業: 農家、夜警、騎士、職人、鉱夫、商人、聖職者、冒険者、猟師、漁師、料理人。
- 見た目はドット絵のパーツ（`static/img/guild-people.svg`）の重ね合わせ: 体 → 脚（ズボンかスカート、性別による）→ 職業の服 → 髪型（5種）→ 帽子。髪色・肌の色・服の2色はパレットから抽選。騎士は男女で鎧の形が違う（女性は胸当てと板金のスカート、兜の代わりにサークレット）。漁師と猟師、職人と鉱夫は同じ服。画像生成は使わない。
- 名前の系統（日本系・ヨーロッパ系・北方系・砂漠系・草原系）を `app.guild.lineage-weights` の重みで抽選する（既定 4:2:1:1:1、ヨーロッパ系が4）。日本系は漢字かひらがな2〜6文字、ほかはカタカナ2〜8文字の名だけ。形式に合わない名前は不正な応答として保存しない。
- 既存の住人と同じ名前や、プレイヤー名（`M_PLAYER` / `M_CK_PLAYER`）を含む・含まれる名前は保存しない（FAILED）。AIはプレイヤー名を受け取らない。有名人・有名作品の人物名はプロンプトで禁止しているだけで、機械的には確認していない。
- AIが決めるのは名前・年齢・紹介・人となりだけ。性別・職業・系統はプロンプトで固定して渡す。
- V55 以前に生まれた住人は系統と見た目が空のまま、従来の単色のドット絵で表示する。

## 毎時の交流（V56）

- 1時間に最大1件。`T_GUILD_HOURLY_JOB.slot_key`（主キー、`yyyy-MM-ddTHH`、JST）と `T_GUILD_INTERACTION.slot_key`（一意）、共通ロックで、複数プロセスや手動実行と重なっても2件目は作られない。処理済み（成功・見送り・失敗）の時間は後から埋めない。
- 参加者は今日の来店者のうち存命（ALIVE）の住人だけ。2人未満なら見送り（SKIPPED）。故人は参加せず、二人がともに親しみ20以上を持っていた故人は「追悼」の題材になる。
- 組の選び方は random / warm（好感度の高い組）/ cold（低い組）/ bond（知人より先の関係）/ thread（未解決の火種がある組）を `app.guild.selection-weights`（既定 3:2:1:2:2）で抽選。合う組がなければ random。直近 `GUILD_RECENT_PAIR_SLOTS`（既定3）件に出た組は1/4の確率に下げる。
- 出来事は `src/main/resources/guild/event-cards.yml`（版 `version` を記録に残す）。daily / progress / thread / major の段階があり、告白・求婚・弟子入り・決裂などの major は酒場全体で1日1件まで。条件（関係・時間帯・数値・火種・成人・年齢差・クールダウン）に合うカードから重みで引き、結果と数値の増減もコードが抽選する。
- 関係は向きのある4軸（信頼・親しみ −100〜100、警戒・恩義 0〜100）と、二人で1つの関係名。関係名を動かすのはコードの規則だけ：
  - 知人→友達（親しみ30以上・3回以上）、知人→仲間（信頼40以上・協力的な交流3回以上。自動冒険がまだないため、相談・協力・手合わせ・指南を協力的な交流として数える）、→親友（親しみ60以上・信頼50以上・8回以上）、親しみが0未満なら知人へ戻る。
  - 恋人：告白カードの成功＋双方成人＋親しみ50以上＋どちらにも恋人・配偶者がいない。配偶者：恋人になって7日以上＋親しみ70以上＋信頼60以上で求婚カードが成功したとき。恋人と配偶者は同時に1人まで。
  - 宿敵：決裂カード＋警戒60以上か親しみ−40以下。知人へ戻るのは和解カードで警戒30未満になったとき。師弟：弟子入りカード＋10歳以上の年齢差＋弟子から師への信頼30以上。
- 火種（約束・借り・遺恨・探し物・片思い）はカードの結果で生まれ、期限（日数）を過ぎると立ち消え（FADED）、対応するカードで片づく（RESOLVED）。
- AIが書くのは情景（120字）とせりふ（2〜6行）だけ。入力は時間帯・種類・決まった結果・二人の年齢/性別/職業/性格・関係・変化・火種で、プレイヤーの情報は含まない。話者が二人以外、または入力にない結婚・交際・宿敵・弟子入り・死を書いた応答は捨てる。
- AIが失敗したとき、`GUILD_INTERACTION_FALLBACK=template`（既定）ならカードの定型文で同じ結果を保存し、`skip` ならその時間を FAILED として見送る。Bedrockは1回最大700出力トークン・45秒。
- 酒場の画面は、今の時間帯（朝0〜11時・昼11〜18時・夜18時〜）に起きた最新の交流があれば、その二人の吹き出しをせりふに替え、下に「いまの酒場」として要約を出す。
- メンテ画面に直近24時間分の実行結果と「この時間の交流を起こす」ボタン（その時間がまだ空いているときだけ交流が起きる）。住人の削除では、その住人が出た交流・関係・火種も消える。
- 未実装：数値気質による補正、週のまとめ、自動冒険との連動。カードの重みや閾値は実データを見て調整する前提。

```properties
GUILD_INTERACTION_INTERVAL_HOURS=1
GUILD_INTERACTION_DAILY_MAX=24
GUILD_INTERACTION_FALLBACK=template
GUILD_RECENT_PAIR_SLOTS=3
```

## 再試行・障害

- 管理者でログインし、メンテページの「今日の住人を追加 / 再試行」を押す。POSTには既存のCSRF保護が必要。
- 1日の上限に達したら追加しない。失敗・素材不足はメンテ画面で確認でき、当日の試行は上限＋5回まで。失敗は「Bedrockの呼び出し」か「応答の形式」かを例外のクラス名付きで表示する。生のAIレスポンスやエラー内容は保存しない。
- 生成は最大850出力トークン、1回45秒のAPI時間上限。外部呼び出しのアプリ側自動リトライはしない（共通SDKの通信リトライは45秒内）。
- DBの共通ロックと日付・出典の一意制約で、複数プロセス・手動と定時の競合を防ぐ。人物、出典、必要なら初回名簿を一つのトランザクションで確定する。
- 正常な生成エラーは `T_GUILD_JOB` にFAILEDとして保存。DB障害やプロセス終了ではトランザクション全体が戻るため、途中の人物は残らず、当日の手動再実行が可能。この場合、ロールバックされた試行回数は残らない。
- 21時にアプリが停止していた日は自動追生成しない。復旧当日に管理者が実行可能。過去日のバックフィル操作は未実装。
- 有効化を止めても既存の人物と最後の来店名簿は閲覧できる。

## プレビューと検証

```sh
./mvnw -Dtest=GuildTests,CognitoSecurityMvpTests test
./mvnw clean package
node --test src/test/js/*.test.cjs
```

`GuildTests` はH2の隔離DBで、同日並列生成、出典重複、非公開情報、権限・CSRF、不正AI出力、再試行上限、人物不足、日付・時間帯、存命以外の除外、名簿固定を確認する。AWSを呼ばず、Bedrock応答はテスト用固定値。`target/guild-preview` に、明示的な架空人物による表示確認用HTMLも出力する。

PostgreSQLでも同じテストを実行できる。**削除可能な専用DBだけ**を指定すること（テストはギルドのテーブルをクリアする）。

```sh
GUILD_TEST_POSTGRES_URL=jdbc:postgresql://127.0.0.1:<port>/postgres \
GUILD_TEST_POSTGRES_PASSWORD=<test-password> \
./mvnw -Dtest=GuildPostgresTests test
```

ローカル実DBは読み取り調査のみ。2026-10-25の確認では、マスタ未連携の7DTD接続記録2件、CKセッション0件、検証済み世界スナップショット0件だった。本番・実ログを使ったBedrock生成はこの実装作業では実施していない。

## 専用ドメイン

まず既存ポータルの `/guild` で利用できる。希望ドメインは未指定のため購入・DNS・公開操作は行わない。

`infra/nginx/guild.conf.example` は同じアプリへの公開用ホスト設定例。`/guild`、`/css/`、`/img/`、`/js/` のみ通し、`/` は `/guild` へ転送する。管理操作とログインは既存ポータル側で行うため、新しいCognitoクライアントや認証コールバックの追加は不要。

接続時には、希望ホスト名・DNSを変更できるアカウント・そのホスト用証明書を用意し、Nginxのホスト名/証明書パスを置換する。`GUILD_PUBLIC_URL=https://<ホスト>/guild` を設定すると酒場のcanonical/OG URLが固定される。実DNS接続と公開は別途行う。
